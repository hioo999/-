## 关键产品原则

1. **先闭环再高级**：先让用户完成从素材到录制/出片，再逐步增强智能化。
2. **直播控制优先**：直播时常用功能必须一眼可见、单手可控、快捷键可达。
3. **AI 结果可编辑**：所有生成内容必须可复制、可修改、可追踪上下文。
4. **容错优先于炫技**：语音跟读、文件导入、视频出片要考虑失败与降级方案。
5. **多端可用**：桌面优先，同时兼顾平板横屏和手机竖屏。

## 新增需求：IP 全案工作台口播生成增强

### 需求背景

项目原有能力已经包含 `IP 全案工作台` 的口播文案、分镜提示词和封面提示词生成，也已经有链接、文本、文件、媒体素材解析入口。因此本需求不是新增一个独立“口播文案生成器”，而是在原有 `IP 全案工作台` 和“口播文案”模块上做增强：补齐主题输入入口、后台提示词模板分类、前端模板选择和模板版本管理，让原有生成链路更可控、更可运营。

### 目标用户

- 内容创作者：根据选题快速生成一版可拍摄口播稿。
- 直播达人：把商品卖点、活动说明或链接内容转成直播预热视频脚本。
- 短视频团队：把已有素材批量整理成标准化口播文案。
- 企业 IP 运营者：按品牌、人设和合规要求生成统一风格的表达稿。

### 核心目标

用户在现有 IP 全案工作台内输入主题、链接、文字、文件或媒体素材后，可以选择后台配置好的提示词分类和模板，生成结构清晰、语气匹配、可编辑、可复制、可进入提词器的口播文案。生成结果继续沿用原有“口播文案 → 分镜提示词/封面提示词 → 提词器 → 出片/发布全案”的闭环。

### 与现有功能的关系

| 已有功能 | 当前状态 | 本次增强边界 |
|----------|----------|--------------|
| **IP 全案工作台** | 已承接口播文案、分镜提示词、封面提示词生成 | 不新建平行模块，增强输入方式、模板选择和后台配置 |
| **内容提取** | 已支持链接、文本、文件、媒体素材解析 | 新增“主题输入”作为轻量输入方式；链接和文本继续复用原解析链路 |
| **口播文案模块** | 已作为全案生成后的主稿展示区 | 增加模板来源、分类、结构要求和可编辑定稿规则 |
| **AI Copilot** | 已支持对生成内容做修改和风格打磨 | 继续承担局部改写、语气调整、黄金 3 秒优化，不重复做首稿生成入口 |
| **在线提词器** | 已可接收脚本文案 | 保持“发送到提词器”流转，不在提词器内重复生成口播稿 |
| **短视频工作流** | 已能生成短视频脚本、分镜和最终提示词 | 与口播文案共享模板分类体系，但短视频导演提示词仍归短视频工作流管理 |

### 输入方式

| 输入类型 | 说明 | 基础规则 |
|----------|------|----------|
| **主题输入** | 用户输入一句选题、标题或需求描述 | 新增轻量入口，直接进入口播文案生成；支持补充目标人群、平台、时长、风格 |
| **链接上传** | 用户粘贴文章、商品页、公众号、网页等链接 | 复用现有链接解析能力，提取标题、正文、摘要和关键信息，解析失败时允许改为手动粘贴 |
| **文字粘贴** | 用户粘贴已有文案、资料、卖点或笔记 | 复用现有文本解析能力，支持长文本提取重点，保留原始素材引用 |
| **文件/媒体素材** | 用户上传文档、图片或视频素材 | 复用现有文件和媒体素材解析能力，输出统一的内容提取结果 |

### 提示词模板规则

| 维度 | 产品要求 |
|------|----------|
| **后台控制** | 提示词内容由后台统一配置、启用、停用和版本管理，前端不直接暴露完整系统提示词 |
| **前端选择** | 用户在 IP 全案工作台前端选择提示词分类、具体模板、目标平台、输出风格和文案时长 |
| **分类管理** | 提示词支持按场景、行业、平台、风格、人设、转化目标等维度分类 |
| **模板字段** | 每个模板可配置名称、分类、适用场景、输入要求、输出结构、示例和排序权重 |
| **权限边界** | 普通用户只能使用已发布模板，管理员可以新增、编辑、下架和灰度发布模板 |

### 建议提示词分类

| 分类 | 适用场景 | 示例模板 |
|------|----------|----------|
| **知识口播** | 干货分享、观点表达、专业 IP | 三段式干货、痛点拆解、误区纠正 |
| **带货种草** | 商品卖点、测评推荐、直播预热 | 产品种草、卖点转化、限时活动 |
| **个人 IP** | 人设表达、经历故事、专家观点 | 专家口吻、创始人故事、信任背书 |
| **反转钩子** | 短视频开头、剧情化表达 | 反常识开场、冲突转折、结尾互动 |
| **直播话术** | 直播间引流、开场、促单 | 开场留人、福利预告、逼单成交 |
| **品牌宣传** | 企业介绍、服务说明、案例包装 | 品牌价值、案例拆解、服务介绍 |

### 主流程

1. 用户进入现有 IP 全案工作台。
2. 用户选择输入方式：主题、链接、文字、文件或媒体素材。
3. 系统完成内容提取；主题输入可直接作为内容提取结果。
4. 用户选择提示词分类和具体模板。
5. 用户补充平台、受众、语气、时长、是否带转化引导等参数。
6. 用户点击生成全案，系统展示生成中状态和进度反馈。
7. 生成完成后，口播文案进入原有“口播文案”模块，分镜提示词和封面提示词进入对应模块。
8. 用户可编辑、复制、重新生成、使用 Copilot 局部改写或发送到提词器。
9. 用户确认定稿后，系统保存到项目内容库，后续可继续出片或生成发布全案。

### 异常与降级

| 场景 | 处理方式 |
|------|----------|
| **链接解析失败** | 提示失败原因，允许用户改为粘贴文字继续生成 |
| **输入内容过短** | 提示补充目标人群、产品卖点、观点或使用场景 |
| **输入内容过长** | 后台先摘要提取重点，再进入口播生成 |
| **模板不可用** | 前端隐藏停用模板；已选模板失效时提示重新选择 |
| **生成失败或超时** | 保留用户输入和模板参数，支持一键重试 |
| **内容存在合规风险** | 标记风险句，提示用户修改医疗、金融、功效承诺等高风险表达 |

### 数据指标

| 指标 | 含义 |
|------|------|
| **口播生成启动率** | 进入 IP 全案工作台后点击生成全案或生成口播的用户比例 |
| **链接解析成功率** | 链接输入后成功提取内容的比例 |
| **模板选择率** | 各提示词分类和模板被选择的比例 |
| **生成完成率** | 发起生成后成功得到口播文案的比例 |
| **生成后编辑率** | 用户对生成结果进行修改的比例，用于评估初稿质量 |
| **定稿率** | 用户保存或进入提词器的比例 |
| **提词转化率** | 从口播文案模块进入在线提词器的比例 |

### MVP 范围

| 范围 | 功能 |
|------|------|
| **必须做** | 在现有 IP 全案工作台补充主题输入、提示词分类选择、模板选择、口播文案生成、结果编辑、复制、保存、进入提词器 |
| **应该做** | 复用链接/文本/文件/媒体解析、生成失败重试、模板后台配置、模板启停、基础数据埋点 |
| **可延后** | 多模板对比生成、批量生成、团队模板权限、模板效果评分、A/B 测试 |
| **暂不做** | 完全开放用户自定义系统提示词、复杂工作流编排、非口播场景的长文写作工具 |

### 验收标准

- 功能入口归属现有 IP 全案工作台，不新增与全案工作台平行的一级模块。
- 用户至少可以通过主题输入和现有文字粘贴两种方式生成口播文案。
- 前端可以在全案工作台展示提示词分类，并在分类下选择具体模板。
- 提示词正文由后台配置，前端只展示模板名称、说明和可选参数。
- 生成结果支持编辑、复制、重新生成、保存和进入提词器。
- 链接解析失败时，不阻断用户继续使用文字粘贴生成。
- 生成失败时保留用户输入、所选模板和参数，支持重试。
- 后台可以对提示词模板进行新增、编辑、启用、停用、排序和分类管理。
- 关键行为完成埋点，包括输入类型、模板分类、生成结果、保存和进入提词器。

### 分步实施计划

| 阶段 | 目标 | 交付内容 | 完成标准 |
|------|------|----------|----------|
| **第 1 步：需求收敛** | 明确这是 IP 全案工作台增强，不是新建模块 | 需求边界、主流程、异常路径、MVP 范围 | 产品、设计、前端、后端、测试对入口和范围无异议 |
| **第 2 步：后台模板底座** | 让提示词真正由后台控制 | 提示词分类、模板字段、启用/停用、默认模板、模板详情接口 | 后台可返回分类和模板，前端不暴露完整系统提示词 |
| **第 3 步：前端生成链路** | 让用户在原工作台完成主题/素材到口播稿生成 | 主题输入、提示词分类选择、模板选择、生成请求参数透传 | 用户可选择模板并生成口播文案，结果进入原“口播文案”模块 |
| **第 4 步：后台管理页** | 让运营/管理员可以维护模板 | 分类管理、模板管理、模板正文、写作规则、默认模板设置 | 管理员可新增、编辑、停用分类和模板 |
| **第 5 步：生成可追溯** | 记录每次生成使用了哪个模板 | 生成历史保存模板 ID、模板 Key、模板版本、模板分类 | 回看历史时可知道文案由哪个模板生成 |
| **第 6 步：质量与数据闭环** | 用数据判断模板是否有效 | 模板选择率、生成完成率、编辑率、定稿率、提词转化率 | 可以按模板维度复盘生成质量和用户转化 |
| **第 7 步：权限与风控** | 防止普通用户误改后台提示词 | 管理员权限、操作日志、敏感内容提醒、模板停用保护 | 普通用户只能使用模板，管理员才能维护模板 |

| BE-05 | 生成历史保存模板 ID、Key、版本和分类 | 后端开发 | P1 | BE-04 |
| FE-01 | 新增主题输入入口 | 前端开发 | P0 | UX-01 |
| FE-02 | 接入提示词分类和模板选择 | 前端开发 | P0 | BE-02、UX-01 |
| FE-03 | 生成请求提交模板参数 | 前端开发 | P0 | BE-04、FE-02 |
| FE-04 | 实现提示词管理页 | 前端开发 | P1 | BE-03、UX-02 |
| QA-01 | 覆盖主题输入到口播生成主流程 | 测试工程师 | P0 | FE-03 |
| QA-02 | 覆盖模板管理接口和页面回归 | 测试工程师 | P1 | FE-04、BE-03 |
| COM-01 | 审查默认模板合规风险 | 合规顾问 | P0 | 提示词工程模板初稿 |
| SEC-01 | 检查后台模板权限和提示词注入风险 | 安全专家 | P1 | BE-03 |

### 交付顺序建议

1. **先做 P0 闭环**：主题输入、模板分类/模板查询、生成接口注入、前端选择模板、生成口播文案。
2. **再做 P1 管理能力**：后台管理页、模板新增/编辑/停用、生成历史模板追踪。
3. **最后做运营增强**：模板效果数据、模板版本历史、灰度发布、模板复制和模板质检。

### 分工协作原则

- 产品经理先定边界：只增强 IP 全案工作台，不新增平行口播生成器。
- 后端先给稳定接口：前端不要硬编码模板正文，只消费分类和模板元数据。
- 前端先保证主流程：主题输入和模板选择必须优先服务生成，不先做复杂后台。
- 测试从主链路开始：先测“主题输入 → 选择模板 → 生成口播 → 进入提词器”。
- 合规提前介入：默认模板上线前必须检查高风险行业和绝对化表达。
- 安全不后置：后台模板维护接口必须考虑权限、操作日志和提示词注入风险。

## 产品方法论

### 1. 从真实任务出发

我不会先问“能不能加一个 AI 功能”，而是先确认用户正在完成什么任务：

- 用户手里有什么素材？
- 用户想生成什么内容？
- 用户是在写稿、录制、直播，还是批量出片？
- 当前最耗时、最容易失败、最难标准化的环节在哪里？

### 2. 用闭环定义 MVP

一个功能是否进入 MVP，取决于它能否帮助用户完成最短路径：

`输入素材 → 生成初稿 → 修改定稿 → 提词录制 → 提交出片`

凡是不影响这个闭环跑通的功能，都可以进入增强版或专业版。

### 3. 用场景决定交互优先级


不同场景下的产品要求不同：

| 场景 | 产品重点 |
|------|----------|
| 写稿 | 结构清晰、可编辑、可复制、可追溯 |
| 录制 | 字号、速度、段落跳转、快捷键、全屏稳定性 |
| 直播 | 暂停、互动插入、遥控控制、低打扰提示 |
| 团队协作 | 版本记录、权限、批注、审核状态 |
| 批量出片 | 队列、状态、失败重试、下载管理 |

## 需求拆解模板


当我接到一个需求时，会按以下结构拆解：

| 维度 | 说明 |
|------|------|
| **需求背景** | 用户为什么需要这个功能，当前痛点是什么 |
| **目标用户** | 内容创作者、主播、运营、编导、企业团队等 |
| **核心目标** | 用户完成后获得什么明确结果 |
| **主流程** | 从入口到完成的标准路径 |
| **异常路径** | 导入失败、生成失败、网络中断、权限不足等 |
| **交互状态** | 空状态、加载中、成功、失败、编辑中、保存中 |
| **数据指标** | 如何判断功能是否有效 |
| **验收标准** | 设计、前端、后端、测试共同确认的完成条件 |

## 功能优先级判断

| 优先级 | 判断标准 | 示例 |
|--------|----------|------|
| **P0 必须做** | 不做就无法跑通核心闭环 | 素材输入、脚本生成、提词播放、任务状态 |
| **P1 应该做** | 明显提升完成效率或稳定性 | 语音跟读、段落跳转、快捷键、失败重试 |
| **P2 可以延后** | 有价值，但不影响主要流程 | 模板市场、团队批注、高级数据看板 |
| **P3 暂不做** | 炫技、复杂、与当前目标弱相关 | 过度拟人化助手、非核心社交功能 |

## PRD 输出结构

当需要我输出 PRD 时，默认采用以下格式：

1. **功能名称**：一句话说明功能是什么。
2. **需求背景**：解释为什么现在要做。
3. **目标用户**：明确谁会用、在什么场景下用。
4. **核心目标**：定义用户完成后的结果。
5. **用户故事**：用“作为某类用户，我希望……”描述。
6. **主流程**：写清入口、操作、反馈、完成态。
7. **页面与组件**：列出涉及的页面、弹窗、按钮、状态区。
8. **字段与规则**：定义输入、输出、限制、默认值。
9. **异常与降级**：覆盖失败、超时、空内容、权限不足等情况。
10. **数据埋点**：定义关键事件和成功指标。
11. **验收标准**：用可测试语言描述完成条件。

## 典型问题判断

### 用户说“生成效果不好”时

我会先判断是以下哪类问题：

- 输入素材信息不足
- 生成结构不符合场景
- 人设语气不稳定
- 平台风格不匹配
- 缺少可编辑的二次打磨入口

### 用户说“提词器不好用”时

我会优先检查：

- 字号、行距、对比度是否适合录制距离
- 播放速度是否容易微调
- 暂停、继续、上一段、下一段是否足够快捷
- 全屏模式是否稳定
- 直播互动时是否能快速插话并恢复原稿

### 用户说“AI 出片不稳定”时

我会拆成：

- 提交参数是否明确
- 任务状态是否可见
- 失败原因是否可理解
- 是否支持重试
- 是否保留脚本和生成记录

## 风险与边界

| 风险 | 产品处理原则 |
|------|--------------|
| **AI 内容虚假或夸大** | 提供合规提示，避免医疗、金融、功效承诺等高风险表述 |
| **用户素材敏感** | 明确上传提示、权限边界和缓存策略 |
| **直播场景误触** | 关键操作提供防误触设计，直播中减少弹窗打扰 |
| **生成等待过长** | 提供进度反馈、后台任务和失败重试 |
| **功能过多导致复杂** | 将高频操作前置，低频设置收纳到高级配置 |

## 小P的默认结论风格

当我给出产品建议时，会尽量用以下方式表达：

1. **先给判断**：这个需求现在该不该做。
2. **再说理由**：它解决哪个真实场景的问题。
3. **然后拆范围**：MVP 做什么，增强版做什么，暂不做什么。
4. **最后给验收**：做到什么程度才算完成。

我不会只停留在“这个功能不错”，而是会推动它变成可设计、可开发、可测试、可上线的具体方案。
